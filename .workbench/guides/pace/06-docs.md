# Docs

1. Docs ship with every phase: the user guide (`docs/`), the developer guide
   (`dev-docs/`, checked against the code) and the design proposal it builds.
2. The user guide says how to use pace, the developer guide what pace does
   today, and the design book (`design/`) holds proposals that are not built.
3. Write short plain sentences in the present tense, with lowercase "pace" and
   British spelling.
4. Name the code: the file, the type, the function.
5. Never describe what the code doesn't do.
6. A restarted page starts with `> **pace-ng:** this page describes the
   restarted pace.`
7. A proposal starts with `> **Status:**
   Idea|Draft|Accepted|Implemented|Rejected` and ends with "What exists today";
   the status table in `design/src/intro.md` follows it.
8. When a proposal is built, the developer guide describes it and the proposal
   is marked *Implemented*.
9. `CHANGELOG.md` files are generated by release-plz and git-cliff; never edit
   them by hand.
10. A commit is a Conventional Commit whose body says what changed and why; the
    `prose` guide holds for it, as for error texts.
